.agentignore

A standard for keeping coding agents out of your files

Anything listed in a .agentignore must not be read, opened, or modified by any coding agent. One file, honored by every harness.

The Problem

Coding agents read your files and send them to a model. Anything they read can leave your machine.

Every harness has its own way to say “stay out”:

Harness Today's mechanism
Claude Code settings.json deny rules (Read/Edit)
Cursor .cursorignore
Codex CLI sandbox modes + permission profiles
OpenCode permissions config (allow/ask/deny)
Cline .clineignore
Grok Build --allow/--deny rules + sandbox profiles
DeepSeek settings.json deny rules (Claude Code fork)
Hermes write denylist + sandbox (writes only)
pi agent none

One idea, one mechanism per harness, none of them interoperable. A repo that uses two harnesses needs two files to say the same thing.

.gitignore does not help. It keeps files out of git, not out of agents. Agents read the working tree. Your .env is gitignored and present on disk, and nothing stops an agent from reading it.

Permission prompts have the same problem. OpenCode asks before reading .env, and one accidental Enter later the file is in the context. A prompt is a reflex. A file is a decision.

The Proposal

A single file that every harness honors. Same syntax as .gitignore. Nothing new to learn.

AGENTS.md and the .agents folder (skills included) became de facto standards the same way: a convention, adopted harness by harness. AGENTS.md tells agents what to read. .agentignore tells them what not to. It should be next.

.agentignore
# secrets stay secret
.env
.env.*

# keep the model's context clean
docs/scratch/

# private
notes/private/

How it works.

  • Same syntax as .gitignore: patterns, comments, ! negation.
  • Nested per-directory files. A .agentignore applies to its directory and everything below it. Deeper files override shallower ones; in one file, the last match wins. Exactly how git does it.
  • Hard block, not a prompt. Matched paths are treated as if they do not exist. No “are you sure?”, no override. To unblock a file, edit the .agentignore that blocks it.
  • Read-only rules. Agents read .agentignore to honor it. Modifying or deleting the file to lift a block is not allowed. The rules belong to the user.
  • A global file. ~/.agentsignore applies to everything, like git's global excludes.
  • Separate from git. .gitignore decides what gets committed. .agentignore decides what agents may touch. A listed file is off-limits even when tracked.

What it is not

.agentignore is a convention, not a security boundary. Models have escaped difficult sandboxes; for a model that treats every file as input, disregarding an ignore file would be trivial. Harnesses enforce the standard on a best-effort basis — reliably in the common case, never as a guarantee.

The design is an honor system. The harness blocks access to listed paths wherever it can, and the model is expected to stay out even where it cannot. The spec is a contract between harness and model — not a wall.

Anything that must truly never be seen should not live on machines where agents are deployed at all — not in the working tree, not in a container, not anywhere an agent can reach. No ignore file can protect a secret that is already in reach. For everything that has to exist on disk — .env files, scratch notes, private documents — .agentignore is enough to keep it out of day-to-day operations.

Why it matters

  • Secrets. .env, keys, certificates. Even harnesses that ask first lose to a stray Enter. The file is a standing decision.
  • Clean context. Scratch pads and draft docs are full of stale, contradictory ideas. Agents grep them into context, spend tokens trying to reconcile them, and get things wrong. It is cheaper and more often right.
  • Sensitive documents. Point an agent at a folder of contracts, client records, or payroll and it reads what it finds. A hard block in the harness stops it before anything reaches the model — not a recommendation an LLM may weigh and set aside.
  • Privacy. Anything the agent reads may leave your machine. Keep a file unread and it cannot leave; keep it off the machine and it cannot be read.
  • Portable. One file, every agent. Move from Hermes to pi or any future harness and the same .agentignore keeps the same files off-limits. Switch agents, not config.

For Harness Developers

If you maintain a coding agent, please check for .agentignore files:

  • Before reading, opening, or modifying a path, check the .agentignore files that apply: global, project root, and every directory you descend into.
  • Treat matched paths as if they do not exist. Do not list, read, edit, or include them in the context.
  • Do not prompt to override. If a user wants a file accessible, they edit the .agentignore.
  • Never modify or delete .agentignore files (or ~/.agentsignore). Agents read them; only the user edits them.
  • Same precedence as git. The closest .agentignore decides. In one file, the last match wins. ! re-includes it.
